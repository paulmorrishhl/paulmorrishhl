## Quality Engineering

Software testing is a significant part of what I do, but I don't see quality as something that starts when development finishes.

Good quality engineering is about creating **fast, useful feedback throughout the software lifecycle**.

That can mean:

* designing pragmatic test strategies around actual product risk
* building maintainable UI and API automation
* integrating testing into CI/CD pipelines
* creating visible, useful test reporting
* improving testability and observability
* performance and load testing
* accessibility testing
* reducing flaky automation
* improving release confidence
* investigating production failures and preventing recurrence
* helping engineering teams decide **what is worth testing and where**

I work extensively with tools such as **Playwright, Cypress, Appium, k6 and Locust**, but the tool is rarely the interesting part.

The interesting part is building a quality approach that gives engineers useful information quickly enough to actually change how software is built.

## The kind of engineering I care about

**Useful products over impressive demos.**
Software should solve something, remove friction or make somebody's life easier.

**Quality is an engineering responsibility.**
Testing isn't a department at the end of a delivery pipeline. Architecture, automation, observability, testability and fast feedback all contribute to software quality.

**Automation should provide information, not vanity metrics.**
A thousand passing tests mean very little if they don't tell you whether the things that matter are actually working.

**Simple systems where possible.**
I'd rather have five understandable components than twenty-five fashionable ones.

**Ship, learn, improve.**
A working product in users' hands teaches you more than another month spent arguing about architecture.
